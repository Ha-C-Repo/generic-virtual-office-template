# Claude Chat vs Cowork vs Code - Explained (k3Bj31-pXOc)

- URL: https://www.youtube.com/watch?v=k3Bj31-pXOc | Uploader: Tim Fairley (ConstructIQ / "Contractor OS") | Duration: 04:18 (257.6s) | Frames: 80 @ 0.311 fps | Transcript source: captions (117 segments, clean)

Thesis: Pick the Claude surface by how much context and how many files the task touches. Chat for single-input/single-output (about 90% of use), Cowork when one job reads and writes many local files in a folder, and Code when the task must reach software outside your desktop (APIs, connectors, scripts).

## The decision rule (Chat vs Cowork vs Code)

His exact, stated criteria, in his own words:

- Chat: "limited context", "asking for specific inputs and outputs", "a single input or maybe two or three inputs and then you have a specific output template you want." Litmus test: "If you can paste everything into one conversation, the best way to do this is with chat." He pegs this at "90% of your Claude usage."
- Cowork: "multiple inputs and multiple outputs." Mechanism: "You select a folder on your desktop ... it can access and read and write to all the files within that folder." Litmus test: "If you're reading and writing to multiple files and you are aware of the risk that it could potentially delete or do unwanted things, so you have to be very specific about what you ask it to do, you should be using co-work." Stated cost: less secure, can go rogue, can delete or edit files you did not ask for. Stated limit: desktop files only, cannot reach external software.
- Code: connect to "external software that is not already built into the customized connectors library within Claude." Use it to "build tools that connect to your accounting software, your construction management software, other ... software apps." Nuance he adds: you do not always need Code first, because pre-built connectors (Google Drive, Notion, Operum, etc.) may already cover the app; Code is for the apps that have no connector. Mechanism: Claude writes and executes its own script against an API (he demos Gmail), "as long as you can describe what you want."

| Surface | Trigger (his words) | Context model | Stated risk | Litmus test |
|---|---|---|---|---|
| Chat | Limited context, specific inputs and outputs, single output template | Whatever you paste or attach into one conversation (plus project files/memory) | Lowest; bounded to the conversation | "Can you paste everything into one conversation?" |
| Cowork | Multiple inputs and multiple outputs | A selected desktop folder; reads and writes all files and subfolders in it | "Much less secure", can go rogue, delete or edit unwanted files; must be very specific; desktop-only | "Reading and writing to multiple local files, and you accept the delete risk?" |
| Code | Connect to external software with no pre-built connector | Reaches outside the desktop via APIs / MCP tools / scripts Claude writes and runs | Not emphasized in the video beyond external-write power | "Need to connect to an app that is not in the connectors library?" |

## What works / what does NOT

Works well, and is shown end to end:
- Chat for a bounded, templated deliverable. One contract plus a saved skill plus a template example produced a clean, structured 24-item departures register, including OCR of an image-only PDF. The skill plus project memory carried the house style so the prompt stayed one line.
- Cowork for fan-out file work. One instruction ("pre populate all my standard templates") generated 31 files across 7 folders with a verify step, and the before/after Word docs prove real population, not placeholder echo. The clarifying-question step before acting and the Progress panel are good safeguards.
- Code for cross-app automation without hand-written scripts. The Gmail classification task ran through MCP tools and a skill, with a plan-first step, and produced a structured Excel artifact.

Does not work or is explicitly cautioned:
- Cowork security. His own words: "much less secure", "potential to go rogue", can "delete all your files" or "edit things you didn't ask for." The mitigation he names is being "very specific" plus the per-folder Allow gate, but he frames this as a real, standing risk, not a solved one.
- Cowork scope ceiling. It cannot touch anything off the desktop; any external-system write forces a move to Code.
- The video is conceptual, not a benchmark. No accuracy check, no timing, no failure case is shown. The departures register and the email classifier outputs are displayed but never validated against ground truth on camera. Treat the demos as illustrative.

## Applicability to a structural steel fabricator (Your Company)

This maps almost one-to-one onto our own Chat / Cowork / Code routing, and it is a useful outside confirmation of how we already split work. The presenter is a general contractor, not a fabricator, so his exact deliverables (departures registers, SWMS, ITPs) are GC-side, but the routing logic transfers cleanly.

- Chat (single input, single output) maps to our bounded Q and A and one-shot reviews: a single contract clause check, an AISC shape lookup, a rate question, a one-page capability blurb, reading a single uploaded RFQ and returning a structured summary. His departures-register pattern is exactly our "verify, do not generate" sweet spot - bounded input, skill-enforced template, low blast radius. This is where a wrong answer is cheap to catch because everything is in one conversation. Our governance fits here: confidence tagging and a single human review step.
- Cowork (multi-file read/write in a desktop folder) is precisely our bid pipeline and per-project context build. Pre-populating a new bid folder from templates, running the bid_chain over a `<bid>/` directory, generating model/render/proposal/-GP artifacts into subfolders, and project-indexer building a 0.ai-context layer - all of that is multi-input/multi-output folder work, which is the textbook Cowork case. His folder-permission gate and "be very specific, it can delete files" warning directly reinforce our existing rules: back up before overwriting (snapshot to _handoff/backups/<UTC-ISO>/), never overwrite FINAL/DELIVERED without a backup, and use the safe_write script for watched files. His clarifying-question-before-acting behavior matches our "ask before guessing" and the SF-sourcing discipline (do not assume the controlling input). The lesson to carry: scope Cowork to the single bid folder, never the whole Desktop, and keep destructive actions behind a confirmation.
- Code (connect to external software with no connector) maps to our dev and automation surface: the Bridge monolith, MCP server, FRED cache, vendor poller, and any future write into accounting, an ERP, or a takeoff/estimating tool. His framing that "you do not always need Code if a connector already exists" is the right default for us too: prefer a connector or an existing Bridge route before writing new integration code. His Gmail-to-Excel classifier is a near-perfect analog for a real Your Company job: classify inbound GC emails for variation / delay / notice exposure, or triage incoming RFQs and bid invitations into a structured sheet. That is a high-value, low-risk Code automation we could actually build.

What does NOT transfer:
- The accuracy stakes are different. His demos generate documents where an error is embarrassing but recoverable. Our bids put dollars on a number. The video shows no validation gate; we must not adopt its "generate and ship" cadence for anything that feeds a price. AISC weights, tonnage, and rates stay on the verify-don't-generate path through aisc_validator.py and the sanity gates regardless of surface.
- His estimating connector is "Operum" (captions say "Opryum"), a GC estimating tool, not anything in our stack. Do not infer we should adopt it.
- His content lives in OneDrive/Desktop with a single user. Our environment has parallel sessions racing on main and a file-watcher that truncates chunked writes to CLAUDE.md, so the naive "let Cowork edit the whole folder" model is more dangerous for us than for him. Keep the existing guardrails.
- Routing nuance for us: because our Cowork (the bid app) and Claude Code both write files, the cleaner split is his - Cowork/agent surface for in-repo and in-bid-folder multi-file work, Code for reaching software with no connector or route. When a task could go either way, prefer the surface with the smaller blast radius and an existing backup/safe-write path.
